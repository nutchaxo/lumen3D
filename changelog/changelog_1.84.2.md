## [ADDED]
- **Stale-code diagnosis that does not need the library**: a new self-contained `api/_code_probe.php`, which calls nothing from `_admin_lib.php`, runs in the `version` action whenever the executing code is older than the files. It still works when the library that executes is an old one that knows nothing about stale code. It reads the version stamped in the library's bytes on disk and compares every served PHP file with the release manifest. For each file that is late it reports its permissions, owner and group, and whether PHP can replace it (a writable file, or a writable folder, since the updater replaces a file by renaming it aside). It also reports the PHP user and what opcache does. From these facts it names one cause: `opcache` (the files on disk are right but old bytecode is still executed), `not_written` (a file on disk was never replaced), or `incomplete` (an update stopped half-way). The result is `codeDiagnosis.probe`. A failure of the probe is logged and never costs the version answer.
- **Release manifest of the PHP code**: the release build writes `api/code-manifest.json`, the SHA-256 of every shipped `api/*.php` and root `*.php` except `install.php`, computed after the version stamp. It ships in the zip and is covered by `SHA256SUMS`. It is what lets the probe say which file is late instead of guessing.
- **Repair from the warning banner**: when a file was not replaced, the banner in Version & updates lists each late file (path, permissions, owner, whether PHP can replace it) and the PHP user. It offers one button, *Repair permissions and reinstall version X*. The button runs the existing permission repair of the Security tab, then reinstalls the version already on disk, then checks again. The repair result is shown in the card. Files that PHP still cannot change are listed with what to do: upload them again by SFTP, or ask the host to give the PHP user write access. Without reinstall support on the executing library, the button runs the permission repair alone and the upload advice is kept.
- **Reinstall the current version**: `update_apply` accepts `{reinstall: true, version: "X.Y.Z"}` on PHP hosts. It downloads and verifies the release exactly like an update (asset name, `SHA256SUMS`, Ed25519 signature) and rewrites every file. It runs only when the published release equals both the files on disk and the requested version; otherwise it answers `409 reinstall_version_mismatch` before downloading anything. A library too old to reinstall answers `409 reinstall_unsupported` instead of falling back to a normal update. The version answer tells the admin whether reinstall is supported (`reinstallSupported`).

## [FIXED]
- **Opcache is cleared in every PHP process, not only one**: on hosts that run several PHP processes or servers, each keeps its own compiled copy. The 1.84.1 recovery, together with its throttle file shared by all of them, let only the first process drop its stale copy. Per-file invalidation now runs in every process that answers while the code is stale, and only the whole-cache reset keeps its one-minute limit. The probe itself invalidates the served files, so a process still executing a pre-1.84.1 library is also cleared.
- **The banner re-checks until the processes are cleared**: after the server dropped its cached code, the tab asks again by itself up to four times, 1.5 s apart. If the warning is still there, the banner explains that other PHP processes of the host still hold the old code and that a PHP restart by the host clears them. While a re-check runs, the buttons are disabled, and a newer check cancels an older one.
- **No raw error code in the banner**: every error the repair or the reinstall can return has a sentence in English, French, Spanish and Dutch.
- **The permission repair names what it could not fix**: `repair_permissions` (PHP and Python) now also returns `failedPaths` (the first 20 entries whose mode could not be changed) and `codeUnwritable` (served code files that PHP can neither write nor replace). The Security tab names up to three of them in its message.
- **Manifest readable after a permission repair**: `api/code-manifest.json` is no longer treated as an `api/` secret, so the repair does not set it to 0600, which would make it unreadable for a PHP user that does not own it.
