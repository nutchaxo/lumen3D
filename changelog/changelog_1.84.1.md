## [ADDED]
- **The server knows which release its code is**: the release build writes its version into `api/_admin_lib.php` (`LUMEN_CODE_VERSION`) and `dev_server.py` (`_CODE_VERSION`), and fails unless the placeholder is found exactly once in each file. A source checkout keeps the placeholder, which means "unstamped": none of the checks below run in development or in the tests.
- **Stale server code is detected**: the `version` action of the admin API now returns `codeVersion` (the release the executing code was built as), `filesVersion` (the newest changelog on disk), `codeStale` and `codeDiagnosis`. When they differ, the PHP host tries to recover (at most once a minute, remembered in `api/.stale-recovery.json`): it finalizes update files parked as `*.lumen-new`, invalidates every served PHP file in opcache, and resets the whole opcache only when per-file invalidation was unavailable or did nothing. It then reports what it found: parked files left, whether opcache is on, `opcache.restrict_api`, `opcache.validate_timestamps`, `opcache.revalidate_freq`, and what the recovery did. The report also says which side is older: code newer than its files means an update stopped half-way. The Python server reports that it was not restarted after its files changed; it never restarts itself.
- **Warning banner in Version & updates**: when the code is older than the files, the tab says which version the server still runs and which version its files are, with the remedy that fits what the server found (rename the parked files, re-check because the server just dropped its cache, wait for opcache's re-read interval, upload the files again, ask the host to clear opcache, run the update again when the code is the newer side, or restart the Python server), the raw opcache facts on a line to forward to the host, and a *Re-check* button. When the server dropped its cache during the very request that reported the mismatch, the tab asks once more by itself before alarming the operator. The banner is hidden while an update runs. The check is repeated on every *Verify*. The text is translated in English, French, Spanish and Dutch.

## [FIXED]
- **Plugin install no longer fails with a cryptic code on a host running old code**: installing a plugin on a server whose executing code is older than its files (the incident on a shared PHP host where the files were 1.84.0 but an older `_admin_lib.php` was still executed, so the Studio placement was refused as `bad_plugin_id`) is now refused up front with `409 stale_server_code` carrying both versions, before any other check, on install and on update, in both backends. The Catalog, the plugin updates and the setup wizard show a sentence naming the two versions and what to do, in English, French, Spanish and Dutch.
- **A placement the platform does not host is named**: a catalog entry for an unknown placement answers `409 unsupported_placement` with the placement instead of `bad_plugin_id`, which is now only for a malformed identifier. The Catalog explains both in the admin's language.

- **No crash when the entry point is newer than its library**: on a PHP host where `api/admin.php` is the new file but the executing `_admin_lib.php` is older, the `version` action reports the mismatch instead of answering 500, and `install_plugin` / `update_plugin` answer `409 stale_server_code` instead of the old `bad_plugin_id`.
- **Login throttle on the Python server**: a plugin install refused before the password was checked (stale code, marketplace not configured) no longer resets the failed-attempt counter.
- **Build refuses a mismatched stamp**: the release build fails unless the newest shipped changelog equals the version it stamps.

## [CHANGED]
- **Unknown placements are listed as incompatible**: the marketplace list marks an entry whose placement this platform does not host as `compat: false` with a reason naming the placement, so its Install button is disabled instead of failing after the click.
- **Limit to know**: a host that already executes pre-1.84.1 code (the incident host) cannot detect itself, because the detection lives in the new code. It needs one manual upload of `api/` (or an opcache clear by the host) to get 1.84.1 running; from then on the check works. If only `api/admin.php` is fresh, the new guards report the mix.
