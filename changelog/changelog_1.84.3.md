## [ADDED]
- **"Try to fix automatically" in the stale-code banner**: a button next to *Re-check* applies every correction the server can make for the situation, then lists what it did and checks again. It puts parked `*.lumen-new` files in place, clears opcache where the host allows it, and refreshes the date of the PHP files that are correct on disk. When a file was not written, it repairs permissions (the Security tab's repair) and then reinstalls the version already on disk. It works beside an old executing library through the new `stale_fix` admin action, which relies on the self-contained probe and calls library functions only when they exist. When PHP must re-read the files, the tab re-checks by itself once that delay has passed and shows the time of that re-check. The separate *Repair permissions and reinstall* button is folded into it. The Python server answers `stale_fix` too: it cannot restart itself, so the button is not shown there.

## [FIXED]
- **Updates now reach hosts where opcache compares file dates**: every entry of every release archive used to carry the same date (1 January 1980), so builds were reproducible. Since PHP 8.0, `ZipArchive::extractTo` copies that date onto the extracted file, and the updater moves the file into place with it. Each update therefore installed files dated exactly like the previous release's. opcache with `validate_timestamps=1` sees a file as changed only when its date changes, so it kept executing the old code indefinitely, and a host whose `opcache.restrict_api` forbids clearing it had no way out. This was found on a shared university host whose `_admin_lib.php` stayed several releases behind its files. Archive entries now carry the release's commit date, and two builds of one commit are still byte-identical. A host stuck this way is freed by a one-click update to 1.84.3, even though that update is still run by its old code.
- **The updater refreshes the date of every file it places**: a file put in place by an update, or swapped in from `*.lumen-new` later, gets the current date, whatever the archive says.
- **The probe refreshes the date of correct files**: when the code that executes is older than files that are correct on disk, the probe and the library's own recovery set the current date on the served PHP files that match the release manifest, so PHP re-reads them at its next check. A file that is itself outdated is never touched. The details line reports `touched=` and the files whose date could not be changed.
- **No more pointless "wait 120 s"**: the banner tells the operator to wait only when the server has actually refreshed the dates. If it could not, or the wait has passed and the code is still old, the banner says so and gives the remaining remedies: upload the files again by SFTP making sure they get a new date (an SFTP client that preserves timestamps does not help), or ask the host to restart PHP.
