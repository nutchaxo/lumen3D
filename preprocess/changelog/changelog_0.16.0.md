# Changelog v0.16.0 (Outil de Preprocessing)

## [ADDED]
* **Le suivi cellulaire d'un timelapse est rattaché tout seul.** Traiter un `.ims` de timelapse produisait un volume et rien d'autre : les trajectoires demandaient de lancer le pipeline de tracking à la main, puis `5-tracking_importer.py` à la main. `run_preprocess.py` cherche désormais l'analyse après l'étape 4 et la rattache dans la foulée. Nouveau module [`tracking_sources.py`](../tracking_sources.py).
* **Trois formes d'entrée acceptées, par ordre de préférence** — l'analyse arrive sous celle que l'opérateur a exportée, et aucune n'oblige à préparer quoi que ce soit :
  1. `<nom>.imaris_track` posé à côté du `.ims` (ou dans un dossier `<nom>/`) : la sortie du pipeline de tracking, surfaces `.glb` comprises.
  2. **le `.ims` lui-même** — Imaris range ses objets Spots/Tracks dans `Scene8/Content`. Rien à poser à côté du volume, rien à ne pas perdre.
  3. `<nom>.xls` / `<nom>.xlsx` — le classeur « export statistics on all tabs », dont la feuille `Position` porte une ligne par spot et par timepoint.
* **Les sources brutes passent par le code d'analyse du labo, pas par une seconde implémentation.** Un `.ims` ou un classeur ne portent que des positions, une appartenance aux pistes et une classification : ni identité cellulaire à travers une division, ni lignage, ni stabilisation. `tracking_sources.py` les normalise en table plate puis appelle `SCRIPTS/Analysis.py` (`standardize_input_dataframe` → `assign_synthetic_track_ids` → `CellIDAssigner` → `stabilize_coordinates`), exactement la séquence de `process_sample`. Un dataset donne donc le même résultat qu'il passe par le pipeline de tracking ou par ce raccourci — vérifié sur les 10 jeux du labo.
* **`5-tracking_importer.py` accepte les trois formes** (`.imaris_track`, `.ims`, `.xls`/`.xlsx`), donc le rattachement manuel d'un dataset déjà traité et l'option [3] du lanceur `RUN.bat` en profitent aussi. Le chemin `.imaris_track` reste **sans dépendance ajoutée** : `pandas`/`xlrd`/`openpyxl`/`orjson` ne sont chargés que pour extraire d'un `.ims` ou d'un classeur.
* **`--tracking auto|off|FICHIER`** : `auto` par défaut, `off` saute l'étape, un chemin impose ce fichier pour tous les datasets traités.
* **`metadata.json` dit d'où vient le tracking** — bloc `tracking.provenance` : la forme source, le fichier, le nom de l'objet Scene8 ou de la feuille, la colonne de classification retenue, le nombre de spots/pistes/cellules. L'information n'est pas récupérable depuis `tracks.json` après coup.
* **Diagnostic sans effet de bord** : `python tracking_sources.py <fichier.ims> --list` liste ce qui serait détecté sans rien écrire.
* **L'exemple livré exerce enfin le tracking embarqué.** Le `.ims` de démonstration généré par `tools/gen_pipeline_examples.py` porte maintenant de vrais objets `Scene8` (Spots, pistes, arêtes de lignage, et les deux niveaux de classification que portent les fichiers du labo), construits à partir de la **même** simulation que le classeur de démonstration. Le pack téléchargeable démontre donc le chemin nominal sans données du labo.

## [OPTIMIZED]
* **Base de temps unifiée entre les trois sources.** Imaris numérote les frames à partir de 1 dans tous ses exports mais à partir de 0 dans `Scene8` ; la lecture de `Scene8` ajoute 1, ce qui aligne les trois entrées sur la convention de `5-tracking_importer.py --timepoint-offset -1`. Validé contre l'export officiel du jeu de référence : **7 564 points sur 30 timepoints, zéro écart**.
* **La classification est retrouvée quel que soit son nom.** Le biologiste la nomme comme il veut (`Region`, `Set 1`, `Point Locations`, `Endothelial cells`, `Location Points`… tous rencontrés). Dans le classeur, on retient donc **la seule colonne que ce n'est pas Imaris qui a écrite** ; dans `Scene8`, le groupe de labels qui couvre le plus d'objets, en préférant celui appliqué aux spots à celui appliqué aux pistes. Le groupe retenu est affiché pendant le run.
* **Classification reprise d'un classeur voisin quand le volume n'en a pas.** Un `.ims` peut porter ses objets alors que la classification n'a été faite que dans la copie d'où les statistiques ont été exportées. Les identifiants Imaris désignant les mêmes spots dans les deux fichiers, les labels sont appariés par id — sans toucher une seule coordonnée (66/66 spots récupérés sur le jeu `TS10c-LSEB-Em5`, qui serait sinon classé `Unknown`).
* **`Scene8` avant le classeur**, parce qu'un classeur peut être périmé : sur `TS11a-NP-Em1-480`, le `.xls` n'a que **155 des 172 spots** du volume (17 ajoutés après l'export), avec **0 coordonnée divergente** sur les spots communs. Sur les 9 autres jeux du labo, les deux sources donnent un résultat **identique** (même nuage de points, même nombre de cellules).
* **Un échec de tracking ne fait jamais échouer le volume** : le dataset est déjà complet et publiable, le tracking est une surcouche. Le message dit ce qui manque (dépendance, source illisible, `Analysis.py` introuvable) et le pipeline continue.

## [FIXED]
* **L'exemple de démonstration ne modélisait pas une division comme Imaris.** Il faisait disparaître la piste mère et apparaître deux pistes neuves ; Imaris fait **brancher la piste existante**, qui porte dès lors deux spots par timepoint — et c'est cette forme-là, pas un changement de `TrackID`, que la détection de mitose lit. L'exemple livré n'exerçait donc jamais le lignage (0 mitose détectée sur une simulation qui en contient une). Corrigé, et les identifiants de pistes suivent maintenant la convention Imaris (`1000000000 + n`), qui garde disjoints les espaces d'identifiants des spots et des pistes — ce dont dépendent les tables de labels de `Scene8`.
